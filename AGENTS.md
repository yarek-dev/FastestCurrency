# Инструкции для работы с Fullstack Bot

## Контекст и границы

Fullstack Bot — Telegram-справочник платных услуг медцентра и веб-интерфейс истории переписки. Это pnpm-монорепозиторий с двумя приложениями:

- `apps/frontend/`: React, TypeScript, Vite, TanStack Router, SWR, Supabase Realtime.
- `apps/backend/`: Supabase Edge Functions на Deno, PostgreSQL, миграции, SQL- и unit-тесты, служебные скрипты.
- `docs/architecture/`: описание архитектуры и исходники C4-диаграмм в PlantUML.
- `.github/workflows/`: отдельные процессы развёртывания frontend и backend.

Перед изменением изучи ближайший код и соответствующие тесты. Подробности находятся в [README.md](README.md), [backend README](apps/backend/README.md) и [описании архитектуры](docs/architecture/README.md). Если документация расходится с реализацией, проверь код и конфигурацию и актуализируй затронутое описание.

Приложения не импортируют исходники друг друга. Общих workspace-пакетов сейчас нет; не добавляй `packages/`, новые слои или инструменты сборки без потребности в задаче. Единственный Supabase-проект находится в `apps/backend/supabase/`.

## Окружение и команды

Используй Node.js 24, pnpm версии из корневого `packageManager` и Deno 2. Зависимости устанавливай из корня через `pnpm install`; в CI — `pnpm install --frozen-lockfile`. Сохраняй единый `pnpm-lock.yaml`, не создавай lockfile npm/yarn. Для Deno используется отдельный общий lockfile.

Все команды в таблице выполняются из корня репозитория:

| Команда | Назначение |
| --- | --- |
| `pnpm dev` | Vite dev server frontend; backend автоматически не запускается |
| `pnpm build` | Production-сборка frontend |
| `pnpm typecheck` | Проверка типов обоих приложений |
| `pnpm test` | Быстрые unit-тесты и компонентные тесты |
| `pnpm test:frontend` | Vitest frontend |
| `pnpm test:backend` | Deno unit-тесты backend |
| `pnpm test:watch` | Наблюдение за быстрыми тестами обоих приложений |
| `pnpm test:db` | Интеграционные SQL-тесты локального Supabase |
| `pnpm test:integration` | Интеграционные HTTP-тесты с локальным Supabase |
| `pnpm test:e2e` | Положительные сценарии в Chromium с локальным Supabase |
| `pnpm supabase start` | Запуск локального Supabase через CLI backend |

Выборочную проверку типов запускай через `pnpm --filter @fullstack-bot/frontend typecheck` или `pnpm --filter @fullstack-bot/backend typecheck`. Отдельных команд lint/format сейчас нет: сохраняй стиль редактируемого файла, не переформатируй соседний код ради единообразия.

## Frontend

- Входная точка — `src/main.tsx`, маршрутизация — `src/router.tsx`. Алиас `@frontend/` указывает на корень приложения, поэтому пути имеют вид `@frontend/src/...`.
- Функциональность чатов находится в `src/modules/chats/`: `pages/`, `hooks/`, `api/`, `types/`. Внешний код подключает модуль через `index.ts`; внутри модуля используй прямые импорты.
- Компонент одной страницы размещай в её `components/`. Поднимай компонент на уровень модуля или приложения при реальном повторном использовании. Не создавай пустые папки на будущее.
- Стили страниц и компонентов — соседние CSS Modules. Общие стили — `src/styles.css`; UI-примитивы — `src/components/ui/`. Здесь shadcn/ui адаптирован под CSS Modules без Tailwind; сохраняй этот подход.
- HTTP-запросы, обработку Realtime-событий и преобразование данных держи в `api/`, управление состоянием и SWR-кэшем — в хуках. Компоненты не должны содержать эту логику.
- `api/chats-subscription.ts` отвечает за подписку, передачу событий и освобождение ресурсов. HTTP-загрузку и восстановление данных выполняют хуки. При изменении подписок сохраняй cleanup и защиту от гонок между HTTP-ответами и событиями.
- Проверяй пользовательское поведение в `apps/frontend/tests/` через Vitest и Testing Library; существующая среда — jsdom, настройка — `tests/setup.ts`.

## Backend

Edge Functions: `telegram-webhook` обрабатывает Telegram updates, `clients` возвращает клиентов с превью, `messages` — страницы истории, `profile` — учебный endpoint.

- Общий import map — `supabase/functions/deno.json`, общий lockfile — `supabase/functions/deno.lock`. `apps/backend/deno.json` подключает их для локальных проверок и скриптов. Все функции в `supabase/config.toml` используют общий import map.
- Алиас `@backend/` указывает на корень backend. В Deno-импортах локальных TypeScript-файлов сохраняй расширение `.ts`.
- В `telegram-webhook/application/` находятся сценарии и порты. `presentation/` разбирает Telegram/HTTP-ввод и формирует ответы. `infrastructure/` реализует обращения к Gemini и работу с базой.
- Передавай реализации портов через аргументы; связывай конкретные зависимости в `telegram-webhook/index.ts`. `application` не импортирует `presentation` или `infrastructure`.
- Общие серверные адаптеры находятся в `functions/_shared/`. Простые HTTP-функции не требуют копирования всей структуры слоёв Telegram-функции.
- При добавлении Edge Function обнови `supabase/config.toml` и список точек входа в backend-команде `typecheck`: сейчас он задан явно.
- Unit-тесты находятся в `supabase/tests/unit/`; внешние API и базу подменяй на границах портов, не делай unit-тесты зависимыми от живых сервисов.

## Данные и поведение, которые нужно сохранять

- HTTP API и frontend должны согласованно обрабатывать `{ items, nextCursor }`, направления `before`/`after` и размер страницы. Сейчас история загружается страницами по 20 сообщений.
- Курсор использует `(created_at, id)`. Не теряй микросекунды времени и точность PostgreSQL bigint: ID передаются строками в ответах API, сравнение больших ID выполняется через `BigInt`, а не `Number`.
- Объединяй сообщения по ID с устойчивым порядком. После переподключения восстанавливай пропущенные сообщения через `after`, сохраняя загруженную историю. Не добавляй polling или сброс кэша без требования задачи.
- При загрузке старых сообщений сохраняй положение прокрутки; автоматическая прокрутка новых сообщений зависит от положения пользователя.
- Для справочника сохраняй векторный поиск через pgvector и приоритет менеджера до и после генерации ответа. Векторы вопроса и данных должны использовать одну модель эмбеддингов и одинаковую размерность.
- Изменения схемы, RPC, индексов, RLS и Realtime-публикаций оформляй новыми миграциями в `supabase/migrations/`. Не переписывай уже применённые миграции. SQL-поведение проверяй в `supabase/tests/database/`.

## Переменные окружения и развёртывание

Примеры переменных — `apps/frontend/.env.example` и `apps/backend/.env.example`. Локальные значения frontend хранятся в `.env.local`, backend — в `.env`. Не включай секреты или локальные env-файлы в код, вывод и коммиты. В браузере допустим только публичный Supabase key; service role и Telegram-токены принадлежат backend. Текущий учебный интерфейс публичный, чтение Realtime ограничивается RLS; не меняй модель доступа попутно с другими задачами.

`pnpm deploy:backend`, `pnpm supabase db push`, `pnpm supabase secrets set` и `pnpm telegram:webhook:set` меняют внешнее окружение. Выполняй их только в рамках задачи, которая разрешает соответствующее развёртывание или настройку; они не являются локальными проверками. Корневой `deploy:backend` развёртывает функции, миграции применяются отдельно.

Frontend workflow публикует `apps/frontend/dist` на GitHub Pages после проверок и сборки; сохраняй поддержку base path. Backend workflow запускается вручную, применяет миграции и затем развёртывает функции. При изменении путей обновляй workspace, lockfile, CI и документацию вместе.

## Проверка результата

При написании нового исполняемого кода добавляй или обновляй тесты в том же изменении. Для исправления ошибки добавляй регрессионный тест, который воспроизводит её. Выбирай самый нижний уровень пирамиды, на котором можно надёжно проверить поведение.

- **Unit.** Проверяй бизнес-правила, преобразования данных, граничные случаи и ошибки. Подменяй внешние зависимости на границах.
- **Integration.** Проверяй взаимодействие компонентов, HTTP-контракты, авторизацию, работу с PostgreSQL, RPC и Realtime. Для проверок, которым нужна база, используй локальный Supabase и изолированные тестовые данные.
- **E2E.** Проверяй только основные успешные пользовательские сценарии в реальном браузере. Негативные сценарии и перебор входных данных проверяй на нижних уровнях.

Тест должен ловить конкретную регрессию. Избегай повторных проверок одного правила на разных уровнях и проверок деталей реализации без наблюдаемого эффекта.

Для изменения frontend запускай его typecheck и тесты; при изменении сборки или интерфейса также `pnpm build`. Для изменения backend запускай его typecheck и unit-тесты; при изменении SQL/RLS/RPC — также `pnpm test:db` в локальном Supabase. Для изменений, затрагивающих оба приложения, запускай корневые `pnpm typecheck`, `pnpm test` и необходимую сборку.

При изменении HTTP-контрактов или доступа запускай `pnpm test:integration`. При изменении основного браузерного сценария запускай `pnpm test:e2e`. Для изменений только документации достаточно проверки путей, команд и diff. Если проверку не удалось запустить, укажи причину в итоговом сообщении.

Имя файла `AGENTS.md` соответствует [официальному формату инструкций Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md).
